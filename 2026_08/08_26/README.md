### 배열(리스트)와 연결 리스트에 걸 맞는 정렬 알고리즘은?

<aside>

### 리스트 ⇒ quick sort

리스트 특징

⇒ 인덱스를 통해 양 끝과 중간을 오갈 수 있음 O(1)

* 퀵 정렬
  ⇒ 퀵정렬의 피벗 선택과 스왑 과정은 임의 접근이 빨라야 효율적임. 또한 연속된 메모리 공간을 사용하므로 캐시 적중률이 매우 높음

</aside>

<aside>

### 연결 리스트 ⇒ merge sort

⇒ 임의 접근은 불가능 하지만 노드 재배치가 쉬움 추가로 특정 위치에 접근하려면 O(n)이 필요하기 때문에 랜덤한 위치에 접근하여 정렬하는 방식에는 불리합니다.

* 병합 정렬
  * 병합 정렬은 순차 접근만으로 정렬할 수 있고 노드의 연결을 변경하는 방식으로 추가 메모리를 사용하지 않고 병합 정렬 방식을 사용할 수 있기 때문에 연결 리스트가 적합하다  
    
    </aside>

### 연결리스트를 게임 개발에서 유용하게 쓰이는 예시

<aside>

### 상태 효과

몬스터에게 걸린 상태이상을 연결리스트로 관리하면 특정 효과만 뽑아서 제거 or 지속시간 순으로 삽입 하기 편함

### 애니메이션 관리

애니메이션 프레임들을 리스트에 저장하고 순차적으로 재상함으로써 애니메이션을 관리함

리스트는 프레임들을 효율적으로 추가 및 삭제하는데 유용하기 때문에 애니메이션의 재생 속도를 조절하는 등의 기술을 구현할 수 있음

### 경로 탐색

경로의 노드들을 연결리스트로 연결. 중간 지점 삽입/삭제(웨이포인트 편집)가 배열보다 자연스러움.

### 페이지 폴트 vs TLB 미스 설명 + 일반적으로 비용이 훨씬 큰 것은?

<aside>

### 페이지 폴트

* 접근하려는 페이지가 아예 물리 메모리에 없는 상태  
  
  </aside>

<aside>

### TLB 미스

* CPU가 접근하려는 논리 주소가 TLB에 없는 경우
* 가상주소 ⇒ 물리주소 변환 정보가 TLB에 없는 상태
* 페이지 자체는 물리 메모리에 존재함  
  
  </aside>

<aside>

### 비용이 훨 큰것

⇒페이지 폴트

> TLB 미스는 이미 메모리에 있는 데이터의 주소 변환 캐시만 다시 채우는 작업이라 메모리 접근 수준에서 끝. 페이지 폴트는 디스크(HDD SSD) 라는 메모리보다 몇 자릿수 느린 저장장치 까지 갔다가 와야함.

추가로 페이지 폴트는 OS 커널 트랩(컨텍스트 스위칭, 페이지 교체 알고리즘 실행 등) 오버헤드까지 붙어서 비용이 더 커짐.

</aside>

### 객체 지향 vs 절차 지향

<aside>

### 객체지향

#### 단점

* 성능 오버헤드
  * 가상함수 호출, 힙할당, 캐시 지역성 저하 등으로 절차지향보다 느릴 수 있음.
* 설계 복잡도
  * 클래스 계층이 깊어지면 오히려 코드 흐름 파악이 어려워짐
* 불필요한 추상화 비용
  * 간단한 스크립트나 일회성 로직에 클래스, 인터페이스를 억지로 씌우면 코드량만 늘어남  
    
    </aside>

<aside>

### 절차지향

#### 장점

* 데이터와 함수가 분리되어 흐름 단순. 캐시 친화적인 배열 기반 처리에 유리

#### 단점

* 전역 상태나 함수 인자로 데이터를 넘기다 보면 코드 규모가 커질수록 데이터 무결성 관리가 어려움
* 코드 재사용이 상속, 다형성 만큼 유연하지가 않음  
  
  </aside>

<aside>

### 정리

> 객체지향은 “구조와 유지보수성”에 절차지향은 “단순함과 성능”에 강점이 있음 실제로는 완전히 한쪽만 쓰기보다 예를 들어 유니티에서 게임 오브젝트, 컴포넌트는 oop구조를 사용하지만 내부적으로 성능이 중요한 부분 (물리,렌더링)은 절차지향 or 데이터지향방식으로 구현하는 식으로 혼합이 일반적

</aside>

### 지역 변수가 스택에 저장되는 이유??

<aside>

### 함수 호출 구조

> 함수 호출은 마지막에 호출된 함수가 먼저 종료되는 구조. FuncA → FuncB → FuncC 순으로 호출되면 반드시 FuncC →FuncB → FuncA 순으로 반환됨. 함수의 호출 및 반환 순서가 스택의 푸시 팝 동작과 정확히 일치하기 때문에 함수가 호출될 때 스택 프레임을 push하고 반환할 때 pop하면 자연스럽게 관리가 됨.

### 할당 해제 비용이 매우 낮음

> 스택은 스택 포인터를 이용해서 sp를 하나만 증가 or 감소 시키면 메모리 할당과 해제가 끝남. 힙처럼 빈 블록을 탐색하거나 단편화를 할 필요가 없어 o(1)에 가까운 비용으로 지역 변수 공간을 마련할 수 있다.

#### 생명 주기가 함수 범위와 정확히 일치

> 지역 변수는 함수가 실행되는 동안만 유효하고 함수가 반환되면 즉시 해제가 되어야함. 스택 프레임이 push될때 생서되고 pop될때 통째로 사라지는 특성이 이 생명주기 요구사항과 정확히 맞차 ㄸ러어짐. 별도의 gc 나 수동해제가 필요 없음

#### 컴파일 타임에 크기를 알 수 있음

> 지역 변수는 대부분 크기가 컴파일 시점에 결정됨. 스택 프레임의 크기를 미리 계산해서 sp를 한 번에 이동시킬 수 있어 힙처럼 런타임에 크기를 협상할 필요가 없음

</aside>

### RR

→ CPU를 사용할 수 있는 시간을 일정한 크기(타임 퀀텀 or 타임 슬라이스)로 잘라서 준비 큐에 있는 프로세스들에게 순서대로 돌아가며 CPU를 배정하는 방식

→ CPU가 사용 중이어도 타임 퀀텀이 끝나면 OS가 강제로 CPU를 빼앗음

* 장점
  * 응답 시간이 짧음.
  * RR은 일정 시간마다 CPU를 넘기기 때문에 각 프로세스가 비교적 빨리 한 번씩 CPU를 받을 수 있음

→ 시분할 시스템, 대화형 시스템, 사용자 응답성이 중요한 시스템

* 단점
  * 타임 퀀텀 크기가 너무 작으면 컨텍스트 스위칭 비용이 커짐.
  * 반대로 너무 커지면 FCFS처럼 변함

#### Round Robin이 CPU 독점을 방지할 수 있는 이유는 무엇인가요?

* **강제 선점(Preemption)이 핵심**  
  Round Robin은 각 프로세스에게 고정된 타임 퀀텀을 할당하고, 그 시간이 지나면 프로세스가 자발적으로 CPU를 반납하지 않아도 강제로 CPU를 회수함. 즉 프로세스의 협조 여부와 무관하게 스케줄러가 통제권을 가져감.
* **모든 프로세스가 큐를 순환**  
  실행이 끝나지 않은 프로세스는 준비 큐의 맨 뒤로 다시 들어감. 그러면 다른 모든 프로세스가 먼저 한 번씩 실행 기회를 얻은 뒤에야 다시 자기 차례가 돌아옴. FCFS처럼 한 프로세스가 끝날 때 까지 CPU를 붙들고 있을 수 없는 구조임.
