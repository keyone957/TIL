### 힙 메모리에 자주 할당 및 해제를 하면 안되는 이유

### 1. GC 의 오버헤드

* 스택 : 함수가 끝나면 메모리 즉시회수

* 힙 : 메모리 즉시회수 X
  
  * GC가 주기적으로 돌면서 Stop the world 현상이 발생하며 프레임 드랍으로 이어짐
  
   
  
  ### 2. 메모리 파편화(단편화)

* 파편화 현상 : 힙에서 다양한 크기의 객체를 넣고 빼다보면 중간중간 작은 구멍들이 생깁니다.

* 압축 비용 : 나중에 큰 객체를 넣어야 하는데 연속된 공간이 없다면 GC는 흩어진 객체를 한곳으로 모으는 압축 작업을 수행함. 이 작업은 CPU에 엄청난 부하를 줌
  
  ### 3. 캐시 적중률

* 스택 : 데이터가 물리적으로 바로 옆에 붙어 있어 CPU 캐시가 한꺼번에 읽어오기 매우 유리함

* 힙 : 데이터가 메모리 여기저기 흩어져 있어 CPU가 매번 먼 길을 돌아 데이터를 가져와야 할 때가 많음
  
  > 힙에 객체가 여기저기 흩어져 할당되면 메모리 접근 패턴이 비연속적으로 될 수 있음. CPU의 캐시는 연속적인 메모리에 접근할 때 효율적이기 때문에 데이터가 메모리에 흩어져 있으면 캐시 미스가 증가하여 성능에 영향을 줄 수 있다.
  
  </aside>
  
  <aside>
  
  #### 정리
  
  > 메모리 단편화가 발생할 수 있고 할당과 해제 자체에도 비용이 발생합니다. 동적 메모리 할당은 단순히 주소를 반환하는 것이 아니라 메모리 관리자가 요청한 크기에 맞는 빈 공간을 탐색하고 해당 공간을 사용 중으로 관리하는 과정이 필요하기 때문에 비용이 발생함. 해제할 때도 해당 메모리를 다시 사용 가능한 공간으로 등록하고 경우에 따라 인접한 빈 공간을 병합하는 등의 관리 작업이 필요합니다
  
  GC에서는 자주 힙할당 및 해제를 반복하면 gc가 사용하지 않는 객체를 찾아 이를 회수하는 과정에서 CPU 부하가 발생할 수 있습니다. 이 과정이 특정 프레임에 집중되면 GC Spike가 발생하여 FPS 가 떨어질 수 있습니다.
  
  </aside>

### 멀티스레딩의 문제점 및 해결 방법

### **`1. Race Condition`**

> 여러 스레드가 같은 공유 데이터에 동시에 접근하여 실행 순서에 따라 결과가 달라지는 문제

ex) 두 스레드가 동시에 하나의 변수에 접근하여 조작하면 원하는 결과가 나오지 않을 수 있음
공유 변수 count=0;
쓰레드 a : count ++; / 쓰레드 b : count++;

#### **해결 방법**

동기화 기법 (뮤텍스, 세마포어, 모니터) 사용

### `2. Critical Section 문제`

> 여러 스레드가 동시에 접근하면 안되는 공유 코드 영역 ⇒ 이 구간에 여러 스레드가 동시에 들어가면 데이터가 잘못될 수 있다.

#### **해결 방법**

임계 영역을 설정하고 상호 배제를 보장한다.
한 스레드가 입계 영역에 진입 → 다른 스레드 대기 → 작업 종료 후 Lock을 해제

### **`3. 데드락`**

> 두 개 이상의 스레드가 서로 상대방이 가진 자원을 기다리며 영원히 멈추는 문제

### **`4. 기아 현상`**

> 특정 스레드가 계속 자원을 얻지 못하고 실행되지 못하는 문제

#### 해결 방법

* 용공정한 스케쥴링 사용

* 대기 시간이 긴 스레드의 우선순위를 높이는 Aging 적용  
  
  </aside>

<aside>

### 정리

멀티스레딩은 같은 프로세스의 메모리를 공유하기 때문에 Race Condition이나 데드락 같은 동기화 문제가 발생할 수 있습니다. 이를 해결하기 위해서는 뮤텍스, 세마포어, 등을 사용할 수 있으며 가장 좋은 방법은 공유 상태와 임계 영역을 최소화 하는것임

</aside>

### 벨라디의 이상현상 : FIFO에서 프레임 수를 늘렸는데 페이지 폴트가 증가하는 이유

<aside>

### 벨라디의 이상 현상

> 프레임 수를 증가시켰음에도 페이지 폴트가 오히려 증가하는 현상

⇒ 대표적으로 FIFO 페이지 교체 알고리즘에서 발생함
ex) 1 2 3 4 1 2 5 1 2 3 4 5
`프레임 3`
→ 페이지 폴트 9번
`프레임 4`
→ 페이지 폴트 10번
**`⇒ 프레임 수를 늘렸는데 오히려 페이지 폴트가 늘어남!`**

#### LRU or OPT에서는 왜 발생하지 않는가?

> 핵심은 프레임 수가 증가했을 때 기존 프레임에 있던 페이지가 계속 포함되는 성질 때문임.  
> 프레임을 증가 시키면 기존 N개의 프레임에서 유지하던 페이지 집합이 N+1개의 프레임에서도 항상 포함되기 때문에 기존에 메모리에 있던 페이지가 제거되는 상황이 발생하지 않기 때문에 페이지를 늘려도 페이지 폴트가 증가하지 않음

</aside>

<aside>

### 정리

> 페이지의 프레임 수를 증가시켰음에도 페이지 폴트가 오히려 증가하는 현상. 대표적으로 FIFO 페이지 교체 알고리즘에서 발생함. FIFO는 최근 사용 빈도나 중요도를 고려하지 않고 메모리에 들어온 순서만 기준으로 페이지를 교체하기 때문에 프레임을 추가했을 때 페이지 교체 순서가 달라지면서 오히려 페이지 폴트가 증가할 수 있습니다.

</aside>

* 다단계 페이지 테이블이 단일 거대 페이지 테이블 보다 메모리를 절약할 수 있는 주된이유?
  
  > 다단계 페이지 테이블 구조는 실제로 사용되는 주소 범위에 필요한 하위 테이블만 생성할 수 있어 희소한 가상 주소 공간에서 메모리 사용을 줄인다  
  > ⇒ 실제로 사용되는 영역에 대해서만 하위 페이지 테이블을 생성하므로 메모리 사용량을 크게 줄일 수 있다.

* 쓰레싱
  페이지 폴트가 자주 발생하는 이유 → 프로세스가 사용할 수 있는 프레임 자체가 적어서
  
  <aside>
  
  ### 정의
  
  > 프로세스가 실제 작업을 수행하는 시간보다 페이지 교체에 더 많은 시간을 사용하는 현상
  
  #### 쓰레싱 흐름
  
  CPU가 프로세스 실행  
  ↓  
  Page Fault 발생  
  ↓  
  디스크에서 페이지 가져오는 동안 대기  
  ↓  
  CPU가 다른 프로세스 실행  
  ↓  
  또 Page Fault 발생  
  ↓  
  디스크 I/O 대기  
  ↓  
  반복
  
  ### 원인
  
  * 과도한 멀티태스킹
    * 동시에 실행되는 프로세스가 많아 각 프로세스가 필요한 메모리를 확보하지 못할 때
  * 작업 집합 크기 초과
    * 실행 중인 프로세스의 작업 집합(Working set : 프로세스가 일정 시간 동안 자주 참조하는 페이지 집합)이 실제 물리적 메모리보다 클 때
  * 메모리 부족
    * 물리적 메모리가 부족할 때
  
  ### 
  
  ### 쓰레싱이 발생하면 나타나는 현상
  
  * 페이지 폴트 급증
  
  * 디스크 I/O증가
  
  * CPU 이용률 감소  
    
    </aside>
  
  <aside>
  
  ### 해결 방법
  
  ### Working set
  
  * 프로세스가 **일정 시간 동안 실제로 인정하는 페이지 집합**을 유지
  * 워킹 셋 크기 만큼 프레임을 확보 못하면 프로세스 중단
  
  ### 지역성 보장
  
  * 지역성
    * 짧은 시간 동안 특정 메모리 영역을 집중적으로 접근하는 성질
  * 시간 지역성
    * 최근에 접근한 코드는 다시 접근될 확률이 높음
  * 공간 지역성
    * 어떤 주소를 접근하면 그 근처 주소들도 함께 접근 될 확률이 높다.
  
  → 지역성 보장이란 프로그램이 일정 시간 동안 자주 사용하는 코드와 데이터를 메모리상에서 집중적으로 접근하도록 하는 것을 의미합니다. 시간 지역성과 공간 지역성을 유지하면 한 번 메모리에 적재된 페이지가 오래 사용되어 페이지 폴트가 감소하고, 그 결과 쓰레싱을 예방할 수 있습니다.
  
  </aside>
  
  <aside>
  
  ### 정리
  
  > 쓰레싱은 프로세스가 실제 작업을 수행하는 시간보다 페이지 교체에 더 많은 시간을 사용하는 현상. 주로 물리 메모리가 부족하거나 동시에 실행되는 프로세스가 많아서 각 프로세스에 충분한 프레임을 할당하지 못할 때 발생합니다.  
  > 이 경우 페이지 폴트와 디스크 IO 가 급증하고 CPU페이지 교체를 기다리는 시간이 늘어나 실제 연산에 사용하는 시간이 감소하면서 시스템 성능이 크게 떨어집니다  
  > 이를 해결하기 위해서는 동시에 실행되는 프로세스 수를 줄이거나 Working Set을 고려하여 충분한 페이지 프레임을 할당합니다
  
  </aside>
