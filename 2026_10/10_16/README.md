## CS 정리

### GC → Garbage Collector

#### Garbage Collector

> 프로그램 실행 중 사용하지 않는 관리 메모리를 자동으로 찾아 회수하는 메모리 관리 시스템

- .NET에서는 CLR이 GC를 제공

#### Garbaage Collection

> GC가 더 이상 사용하지 않는 객체를 식별하고 해당 메모리를 회수하는 작업자체

### Mark and Sweep 알고리즘 → GC 공통된 알고리즘

> 살아 있는 객체를 표시하고 참조되지 않는 객체를 회수하는 방식의 알고리즘

1. 루트에서 시작하여 참조되고 있는 모든 활성 객체탐색
2. 살아 있는 객체를 표시 (Mark)
3. 표시되지 않은 객체들을 Sweep하여 메모리를 해제함

#### 수행과정

1. **Mark** : 루트부터 연결된 살아있는 객체를 찾아서 mark함
2. **Sweep** : 마크되지 않은 객체는 더이상 사용되지 않는 것으로 간주하여 해제함
3. 사라진 객체가 차지한 공간을 제거하고 살아 있는 객체를 메모리 압축을 통해 메모리 단편화를 방지한다 → 이 압축과정에서 SOH는 압축을 통해 메모리 단편화를 방지하지만 LOH는 압축 과정이 없어서 외부 단편화가 발생할 수도 있음

---

### .NET의 GC

> 세대 기반 GC 사용.  
> 객체의 생존 기간에 따라 세대를 구분하고 일반적으로 수명이 짧은 객체가 많이 낮은 세대를 더 자주 수집하여 GC 비용을 줄이는 방식.

⇒ 메모리 할당량이 임계값에 도달하거나 메모리 압박이 발생하는 등의 상황에서 실행됨

낮은 세대의 수집만으로 충분한 메모리를 확보하지 못하면 상위 세대 까지 수집범위를 확대할 수 있다.

#### 세대를 나누는 이유

> 최근 생성된 객체는 대부분 금방 버려지고, 오래 살아남은 객체는 계속 살아남을 확률이 높음. 그래서 전체 힙을 매번 뒤지지 않고 어린 세대부터 수집함

| 세대  | 설명                                                                    |
| --- | --------------------------------------------------------------------- |
| 0세대 | 새롭게 생성된 객체 ⇒ 가장 자주 수집                                                 |
| 1세대 | 0세대 GC에서 살아남은 객체, 임시 객체가 아닌 객체                                        |
| 2세대 | 오래 살아남은 객체 + LOH/ 최소 2회에서 수차례 동안 GC에 의해 수집되지 않은 객체 ⇒ 상대 적으로 수집 빈도가 낮음 |

→만일 2세대 힙이 가득 찬다면 CLR은 어플의 실행을 잠시 멈추고 FULL GC를 수행하여 0~2세대까지의 전체에 걸쳐 쓰레기를 수집함.

**.NET의 GC는 메모리 압축을 통해 흩어져 있는 객체들을 한 곳으로 모으는 압축과정을 거쳐 메모리 파편화가 적음.**

#### SOH 와 LOH

- SOH
  - 0,1,2 세대에  할당되는 작은 객체들이 저장되는 메모리 영역. 일반적으로 85KB 이하의 객체들이 SOH에 저장된다.
- LOH
  - 논리적으로는 2세대에 속해서 2세대 GC때만 해제됨
  - 일반적으로 85KB 이상의 크기를 가진 객체들이 이 LOH에 저장이 되는데 GC가 동작할 때 LOH에 있는 객체들은 압축을 하지 않는다 ⇒ 큰 메모리 블록을 이동시키는 비용 때문에 메모리 압축 X
  - 이는 2세대 GC가 발생할 때 같이 해제가 됨

### 유니티의 GC

#### 수행과정 → 보헴 알고리즘 사용 (보수적임)

1. 세대 구분 없이 모든 메모리를 다 돌면서 사용중인 객체를 마킹
2. 마킹되지 않은 객체를 메모리 해제 시켜줌

#### 보헴 알고리즘의 특징

1. 보수적
   
   - 사용 중일 가능성이 조금이라도 있는 객체는 지우지 않음.
   - 따라서 실제로는 사용하지 않는 객체가 남을 수도 있음 ⇒ 의도치 않은 메모리 누수가 일어날 수 있음

2. 세대 구분 없음
   
   - 항상 힙 전체를 스캔 ⇒ 힙이 커질수록 정지 시간도 비례해서 증가

3. 메모리 압축 없음

4. Stop the world
   GC 수행하는 동안 실행을 일시적으로 중단
   
   ```text
   게임 실행
      ↓
   GC 발생
      ↓
   게임 메인 스레드 중단
      ↓
   GC 작업 수행
      ↓
   게임 실행 재개
   ```

---

#### **점진적 GC-> Incremental GC**

> 한 번에 수행하던 GC 작업을 여러 구간으로 나누어 처리함으로써 한 번의 긴 중단을 줄이는 방식

- 이것은 gc생성이 줄어드는 것이 아닌 단지 stop the world 를 보완하기 위해 나온 것.

기존 GC

```text
Frame 1    정상 실행
Frame 2    정상 실행
Frame 3    ───── GC 작업 ─────
Frame 4    정상 실행
```

점진적 GC

```text
Frame 1    게임 + GC 일부
Frame 2    게임 + GC 일부
Frame 3    게임 + GC 일부
Frame 4    게임 + GC 일부
```

GC Spike ⇒ 가비지 컬렉션(GC)이 실행되면서 CPU 처리 시간이 순간적으로 증가해 프레임 시간이 급격히 늘어나는 현상

GC 작업이 한 프레임에 집중되는 것을 방지하여 GC Spike를 완화할 수 있음

---

### 정리

#### GC란?

> 관리 힙에 할당된 객체 중 더 이상 접근할 수 없는 객체를 찾아 메모리를 자동으로 회수하는 시스템  
> GC Root를 기준으로 도달 가능한 객체를 탐색하고 도달할 수 없는 객체를 회수하여 해당 메모리 공간을 재사용할 수 있도록함

#### .NET 과 유니티 GC 차이

> .NET은 세대별 가비지 컬렉션을 사용하며 주로 짧은 수명의 객체가 많은 낮은 세대를 자주 수집함 또한 메모리 압축을 통해 단편화를 줄일 수 있음  
> 유니티는 비세대별 비 압축형 GC를 사용하므로 메모리 단편화가 발생할 수 있습니다. 그리고 GC 작업으로 인한 프레임 스파이크를 완화하기 위해 점진적 GC 를 활용할 수 있습니다.
