### GameObject VS Component

#### GameObject

씬을 구성하는 기본 객체 단위 ⇒ Component들을 담는 그릇 역할

#### Component

GameObject에 부착되어 실제 기능을 담당하는 요소

#### 정리

GameObject는 유니티 씬을 구성하는 기본 객체 단위이며 Component를 담는 컨테이너 역할을 합니다.Component는 GameObject에 부착되어 물리, 충돌, 게임 로직 등의 실제 기능을 담당합니다.유니티는 게임 오브젝트에 여러 컴포넌트를 조합하여 객체의 기능을 구성하는 Component 기반 구조를 사용합니다.

### 상속 vs 합성

#### 상속 - is a (즉, 어떤 객체가 더 큰 개념의 **특수한 종류**라면 상속을 고려할 수 있다.)

자식 클래스가 부모 클래스의 속성과 기능을 물려받아 확장하는 `is a` 방식입니다.

**장점**

1. 코드 재사용성 증가
2. 유지보수 용이
3. 확장성 증가

**단점**

1. 클래스 간 결합도 증가
   → 부모 클래스가 변경되면 자식 클래스에도 영향을 주기 때문에 의존성이 높아짐. 구조가 복잡해질수록 유지보수가 어려워짐

2. 조합 폭발
   → 특성이 조합될 때마다 새로운 클래스가 필요해져 클래스 수가 기하급수적으로 늘어남

3. 런타임 변경 불가
   → 컴파일 타임에 구조가 고정되어 객체 생성 이후 행동을 바꿀 수 없음

#### 합성 - has a (즉, 어떤 객체가 다른 객체를 **구성 요소로 포함**하고 있을 때이다.)

객체가 다른 객체를 멤버로 가져서 그 기능을 활용하는 `has a` 방식입니다.

→ 필요한 기능을 직접 상속받는 대신 다른 객체를 내부에 포함해서 조합하는 방식

**장점**

* 유연함
* 필요한 기능만 조합 가능
* 결합도 낮음
* 런타임에 구성 변경 쉬움

**단점**

* 설계 초기에 구조를 잘 나눠야 함
* 객체 수가 많아질 수 있음
* 단순한 경우에는 상속보다 코드가 길어질 수 있음

#### 정리

상속은 공통 로직을 부모에 두고 재사용하기 좋지만, 특성 조합이 늘어날수록 클래스 수가 폭증하고 런타임에 행동을 바꿀 수 없다는 한계가 있습니다.합성은 기능을 독립된 객체로 분리해 조립하는 방식이라 재사용성과 런타임 유연성이 높지만, 설계 초기에 역할을 잘 나눠야 하고 객체 수가 늘어날 수 있습니다.실제로는 Unity의 GameObject-Component 구조처럼, 계층이 명확하고 단순한 경우엔 상속을, 기능 조합이 다양해지거나 유연성이 필요한 경우엔 합성을 선택하는 것이 일반적입니다.

### 함수형 프로그래밍

#### 함수형 프로그래밍

프로그램을 상태 변경보다는 함수의 조합과 데이터 변환을 중심으로 구성하는 프로그래밍 방식입니다.⇒ 값을 직접 계속 바꾸기보다는, 입력값을 함수에 넣어서 새로운 결과값을 만들어냅니다.

ex)
    int Add(int a, int b)
    {
        return a + b;
    }

    int value = Add(10, 5);

⇒ 입력 → 함수 → 결과의 형태

#### 특징

1. 순수 함수
   같은 입력이면 항상 같은 결과를 반환하고 외부 상태를 변경하지 않습니다.
      int Add(int a, int b)
      {
   
          return a + b;
   
      } // 언제나 1과 1을 넣으면 2가 나옴

      int _score;
    
      void AddScore(int value)
      {
          _score += value;
      }
      // 이는 _score 값을 변경하고 있기 때문에 부수 효과가 있는 함수.

2. 불변성
   기존 데이터를 수정하기보다는 새로운 데이터를 만들어 사용합니다.

3. 부수 효과 최소화
   전역 변수 수정, 파일 저장, 외부 객체 변경 같은 함수 외부에 영향을 미치는 동작을 줄입니다.

4. 함수를 값처럼 사용
   함수를 변수에 저장하거나 다른 함수의 매개변수로 전달할 수 있습니다.

5. 함수 조합
   작은 함수들을 조합해서 복잡한 동작을 구성합니다.

#### 장점

* 순수 함수는 외부 상태에 의존하지 않아 테스트와 디버깅이 쉬움
* 상태 변경이 없어 멀티스레드 환경에서 안전
* 함수 단위로 로직을 조합하므로 재사용성이 높다

#### 단점

* 불변 데이터를 다루기 위해 매번 새 객체를 생성하므로 메모리 할당이 늘어날 수 있음

### 함수형 프로그래밍 vs 객체지향 프로그래밍

⇒ 무엇을 중심으로 코드를 구성하는가?

#### 객체지향 프로그래밍

데이터(상태)와 그 데이터를 다루는 함수(행위)를 하나의 객체로 묶어서, 객체 간 상호작용으로 로직을 구성합니다.
    class Player {
        private int hp = 100;  // 상태를 가짐

        public void TakeDamage(int dmg) {
            hp -= dmg;  // 객체 내부 상태를 직접 변경
        }
    }

⇒ 상태(hp)가 객체 안에 있고 메서드 호출로 그 상태가 바뀜

#### 함수형 프로그래밍

상태를 직접 변경하지 않고, 입력을 받아 새로운 결과를 반환하는 순수 함수의 조합으로 로직을 구성합니다.
    int TakeDamage(int hp, int dmg) => hp - dmg;
    // 기존 hp를 바꾸지 않고, 새로운 hp 값을 반환
    int newHp = TakeDamage(player.hp, dmg);

⇒ 상태를 바꾸는 대신 새 값을 만들어 반환.
    // 객체지향 - 리스트 안의 몬스터 상태를 직접 변경
    foreach (var monster in monsters) {
        monster.TakeDamage(10);  // 각 객체의 내부 상태가 바뀜
    }

    // 함수형 - 기존 리스트는 그대로 두고 새 리스트를 생성
    var damagedMonsters = monsters
        .Select(m => m.WithHp(m.Hp - 10))  // 새 값을 가진 새 객체 반환
        .ToList();

#### 비교표

|        | 객체지향             | 함수형                         |     |
| ------ | ---------------- | --------------------------- | --- |
| 중심 단위  | 객체               | 함수                          |     |
| 상태 처리  | 객체 내부 상태를 직접 변경  | 상태 변경 없이 새 값 반환             |     |
| 핵심 개념  | 캡슐화, 상속, 다형성     | 순수 함수, 불변성, 고차 함수           |     |
| 코드 재사용 | 상속 / 합성으로 구조 확장  | 함수 조합(합성)으로 로직 확장           |     |
| 디버깅    | 객체 상태 추적 필요      | 입출력만 보면 됨                   |     |
| 멀티스레드  | 공유 상태로 인해 동기화 필요 | 상태 변경이 없어 상대적으로 안전          |     |
| 메모리 측면 | 추가 할당 없음, 가벼움    | 변경마다 새 객체 생성 ⇒ 할당 증가, GC 부담 |     |

### 스택 포인터란?

#### 스택 포인터

CPU 안에 있는 레지스터(저장 공간) 중 하나로, 그 안에 현재 스택의 최상단 메모리 주소를 담고 있습니다.

⇒ SP 자체는 저장 공간이고, 그 저장 공간에 담긴 값이 스택의 현재 위치(주소)를 가리키는 포인터 역할을 함

#### 정리

스택 포인터는 현재 스택의 Top 위치를 가리키는 CPU 레지스터입니다. 함수 호출이나 지역 변수 할당 등으로 스택이 사용될 때 스택 포인터가 이동하며, 함수가 종료되면 이전 위치로 복구됩니다.스택 포인터 자체에는 스택 데이터가 아니라 현재 스택 위치를 나타내는 주소값이 저장됩니다.
