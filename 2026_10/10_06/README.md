## CS 공부 및 정리

### 행렬 / 역행렬

#### 행렬

숫자를 격자 형태로 배열한 것

#### 역행렬

어떤 행렬 A에 곱했을 때 단위행렬 I가 되는 행렬 $A^{-1}$⇒ 원래 변환을 완전히 되돌리는 행렬

* 단위 행렬 ⇒ 곱해도 원래 값이나 행렬을 그대로 유지시키는 행렬

공식 (2x2 행렬)

$$
A = \begin{pmatrix} a & b \\ c & d \end{pmatrix}, \quad A^{-1} = \frac{1}{ad-bc}\begin{pmatrix} d & -b \\ -c & a \end{pmatrix}
$$

1. 행렬식 계산 ⇒ ad-bc가 0이면 역행렬 존재 X
2. 각 원소의 위치를 바꾸고 부호를 조정
3. 행렬식의 역수를 곱함

### 행렬의 쓰임새

⇒ 주로 좌표 변환할 때 사용

#### 1. World 행렬 (Local 좌표 ⇒ World 좌표로 배치)

오브젝트 고유의 좌표를 실제 게임 월드의 어느 위치에 어떤 회전과 크기로 놓을지 결정하는 행렬

> World 행렬 = Scale 행렬 x Rotation 행렬 x Translation 행렬

예시)

한 모델을 만들 때 원점 0 0 0 기준으로 모델링. 이 모델을 게임 월드의 10 0 5 위치에 45도 회전시켜서 2배 크기로 배치하고 싶다면 World 행렬이 이 세 가지 변환을 하나로 합쳐서 모델의 모든 정점에 곱해줌.

#### 2. View 행렬 (월드 좌표를 카메라 기준 좌표로 배치)

월드 좌표를 카메라가 원점에 있고 정면을 바라본다고 가정했을 때의 좌표로 바꾸는 행렬

> View 행렬 = 카메라의 World 행렬의 역행렬

카메라가 움직이거나 회전해도 실제로는 모든 오브젝트의 위치를 다시 계산하는 것이 아님. 카메라 기준으로 상대적인 위치만 계산하면 됨.예를 들어 카메라가 오른쪽으로 5만큼 이동했다면 모든 오브젝트가 왼쪽으로 5만큼 이동한 것처럼 보이게 처리

⇒ 카메라도 월드 안의 하나의 오브젝트이므로 World 행렬을 가지는데, 그 역행렬을 모든 오브젝트에 곱하면 카메라가 원점에 고정되어 있을 때의 상대 좌표로 변환됨.

#### 3. Projection 행렬 (3D를 2D 화면에 투영)

카메라 기준 3D 좌표를 실제로 화면에 그려질 2D 평면 좌표로 압축하는 행렬

> 최종 화면 좌표 = Projection 행렬 x View 행렬 x World 행렬 x 정점 좌표

GPU의 정점 셰이더 단계에서 모든 정점에 이 세 행렬을 순서대로 곱해서 최종적으로 화면에 그려질 픽셀 위치가 결정됨 ⇒ 렌더링 파이프라인의 가장 첫 단계가 이 연산

### 역행렬의 쓰임새

#### 부모 ⇒ 자식 로컬 좌표로 변환

월드 좌표에 있는 특정 오브젝트 기준의 로컬 좌표로 바꿀 때 사용 // 월드 좌표를 부모 기준 로컬 좌표로 변환 Vector3 localPos = parent.worldToLocalMatrix.MultiplyPoint(worldPos);

⇒ 부모의 World 행렬이 "로컬 → 월드"로 변환하는 행렬이므로 그 역행렬은 "월드 → 로컬"로 변환함. 자식 오브젝트를 부모에 붙이거나 특정 오브젝트 기준으로 상대 위치를 계산할 때 필요.

#### 마우스 클릭 레이캐스팅

화면의 2D 클릭 좌표를 3D 공간의 광선으로 되돌릴 때 사용

> 월드 좌표 ≈ View행렬⁻¹ × Projection행렬⁻¹ × 화면 좌표

Projection·View 행렬이 3D → 2D로 변환했던 과정을, 역행렬을 곱해서 거꾸로 풀어냄

### 성능이 중요한 모바일 환경에서 왜 URP를 사용할까?? ⇒ 빛이 많아지면 연산량이 늘어나지 않나?

모바일 환경에서 Forward Rendering을 많이 사용하는 이유는 실시간 라이트 수가 많지 않은 상황에서는 구조가 단순하고, Deferred Rendering처럼 여러 개의 G-Buffer를 생성하고 다시 읽는 과정이 필요하지 않아 메모리 사용량과 메모리 대역폭 부담을 상대적으로 줄일 수 있기 때문입니다.

모바일에서는 데스크톱 GPU에 비해 사용할 수 있는 메모리 용량과 메모리 대역폭, 전력과 발열 여유가 상대적으로 제한적입니다. 특히 화면 해상도가 높아질수록 프레임마다 많은 픽셀 데이터를 메모리에 쓰고 다시 읽는 작업 자체가 큰 비용이 될 수 있습니다.

Forward Rendering은 오브젝트를 렌더링하면서 바로 조명을 계산하기 때문에 G-Buffer가 필요하지 않아 이러한 부담이 상대적으로 적습니다.

다만 Forward Rendering도 단점이 있습니다. 한 오브젝트에 영향을 주는 실시간 라이트의 수가 많아질수록 각 라이트에 대한 조명 계산량이 증가하기 때문에 라이트가 많아지면 성능이 떨어질 수 있습니다.

그래서 모바일에서는 일반적으로 실시간 라이트 수를 제한하고, Lightmap이나 Baked Lighting, Light Probe 등을 활용해 실시간 조명 계산을 줄입니다. 그래도 많은 실시간 라이트가 필요한 경우에는 Forward+나 Deferred Rendering을 고려할 수 있습니다.

즉, 모바일에서 Forward Rendering을 사용하는 이유는 라이트가 많아도 무조건 빠르기 때문이 아니라, 실시간 라이트 수를 제한한다는 전제에서 메모리와 대역폭 사용량을 줄이고 비교적 단순한 렌더링 구조를 사용할 수 있기 때문입니다.
