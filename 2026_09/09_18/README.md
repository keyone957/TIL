## CS 공부

### C#에서 값 타입의 변수나 필드(int, float, bool, enum, struct 등)는 모두 스택에 저장되나요? 참조 타입의 변수나 필드(class, string 등)는 모두 힙에 저장되나요?

무조건 힙과 스택에 저장되는 것은 아님!

* 클래스의 인스턴스 필드는 해당 필드가 값 타입으로 선언되어 있더라도 인스턴스의 원본 데이터가 힙에 저장되므로 함께 힙에 저장된다.

* 문자열은 힙도 스택도 아닌 literal 영역에 실제 데이터(intern)가 할당되고 이것의 위치(주소)를 변수에 들고 있게 된다.
  
  * 문자열이 지역 변수로 선언되었다면 주소 값이 스택에 존재
    
    * `코드`
      
          // 1. 지역 변수로 선언 → 주소 값이 스택에 존재
          void Method()
          {
              string localStr = "Hello"; 
              // "Hello"라는 실제 데이터는 
              //인턴 풀(literal 영역)에 존재
              // localStr 변수(그 데이터를 가리키는 주소)는 
              //스택에 저장
          }

* 문자열이 클래스의 인스턴스의 필드로 선언되었다면 주소 값이 힙에 존재한다.
  
  * `코드`
    
        class Player
        {
            public string Name = "Player";
            //이 필드는 플레이어 객체와 함께 힙에 존재
        }
        
        Player player = new Player();
        player.Name="wongi";
        //wongi라는 실제 데이터는 인턴 풀에 존재
        // Name 필드는 player 객체(힙) 안에 함께 저장됨

* 배열은 대부분 힙에 저장됨.

### 유니티 GC 특징 + 보헴 알고리즘 특징

#### 수행과정 → 보헴 알고리즘 사용 (보수적임)

1. 세대 구분 없이 모든 메모리를 다 돌면서 사용중인 객체를 마킹
2. 마킹되지 않은 객체를 메모리 해제 시켜줌

#### 보헴 알고리즘의 특징

1. 보수적
   * 사용 중일 가능성이 조금이라도 있는 객체는 지우지 않음.
   * 따라서 실제로는 사용하지 않는 객체가 남을 수도 있음 ⇒ 의도치 않은 메모리 누수가 일어날 수 있음
2. ~~메모리 단편화를 줄이기 위해 메모리 풀 기법을 사용한다~~
3. 세대 구분 없음
   * 항상 힙 전체를 스캔 ⇒ 힙이 커질수록 정지 시간도 비례해서 증가
4. 메모리 압축 없음
5. Stop the world
   * 마킹 + 스윕이 끝날 때까지 전체 스레드 정지

* * *

#### 위 약점에 대한 보완책

* **`점진적 GC → Incremental GC`**
  * 기존 보헴 같은 경우 GC가 실행되는 동안 프로그램이 멈추지만, 점진적 GC를 사용하면 여러 프레임에 걸쳐 조금씩 나눠서 GC가 동작합니다.
  * 이것은 GC 생성이 줄어드는 것이 아닌 단지 stop the world를 보완하기 위해 나온 것.

### const vs readonly

상수를 나타내는 값을 정의할 때 사용하는 키워드

| 항목        | `const`                 | `readonly`                |
| --------- | ----------------------- | ------------------------- |
| 초기화 시점    | 선언 시 (무조건)              | 선언 시 or 생성자               |
| 값 변경      | ❌ 절대 불가                 | ❌ 생성자 이후 변경 불가            |
| 타입 제한     | 리터럴 타입만 (int, string 등) | 모든 타입 가능 (클래스, 구조체 등)     |
| static 여부 | 자동 static               | 수동으로 `static readonly`    |
| 값 결정 시점   | 컴파일 타임                  | 런타임                       |
| 예시 용도     | `PI`, 물리 상수 등           | 사용자 ID, 설정값 등 실행 시 결정되는 값 |

* const는 컴파일 타임 상수
* readonly는 런타임 상수
* 값이 참조 타입이거나 런타임에 정해지면 readonly 사용
* const는 값 수정 시 재컴파일 필요
* readonly는 부분 빌드만 해도 다른 곳 적용됨

### const

`컴파일 타임`에 값이 확정되는 상수
    public const double PI = 3.14159;
    public const int MaxPlayer = 4;

* 컴파일 시점에 값을 먼저 초기화 시켜야함
* 리터럴 타입(int, string, bool, enum 등)만 가능
* 런타임에 생성되는 객체(new)는 불가.
* 값 수정 시 재컴파일이 필요함
* 사용하는 쪽 코드에 값 자체가 그대로 복사(인라인)됨 ⇒ 컴파일 타임 값 치환
* 자동 static

### readonly

`런타임`에 값을 결정할 수 있지만 초기화 이후에는 변경할 수 없는 필드
    public class Player
    {
        public readonly int Id;
        public static readonly DateTime ServerStartTime = DateTime.Now; 
        // 런타임에 결정

        public Player(int id)
        {
            Id = id; // 생성자에서 초기화 가능
        }
    }

* 값을 선언 시점 또는 생성자 안에서 초기화 가능(생성자가 끝나면 그 이후로는 변경 불가) ⇒ 값을 런타임 중에 세팅 가능
* 모든 타입 가능
* static을 붙이지 않으면 인스턴스마다 다른 값을 가질 수 있다
* 참조가 실제로 저장된 메모리 위치를 그대로 참조함 ⇒ 인라인 복사 X

### 재컴파일 문제

    // A.dll
    public const int Version = 1;
    
    // B.dll (A.dll을 참조)
    Console.WriteLine(Version); // 컴파일 시 "1"이 B.dll에 그대로 박혀 들어감

여기서 나중에 `A.dll`만 `Version = 2`로 바꿔서 새로 빌드해도, **B.dll을 재컴파일하지 않으면 여전히 1이 출력됨**. const는 컴파일 시점에 값이 사용하는 쪽 코드에 복사돼서 박히기 때문.

반면 `readonly`로 선언했다면 `A.dll`만 새로 빌드해도 `B.dll`은 재컴파일 없이 실제 값이 반영된 최신 값을 참조함. `readonly`는 참조를 통해 값을 읽어오는 거라 원본이 바뀌면 그대로 반영됨.

### 적절한 사용처

* **절대 안 바뀔 값** (수학 상수, 게임 내 절대 규칙값) → `const`
* **초기화 시점에 계산되거나, 나중에 바뀔 가능성이 있는 값** → `readonly`

### 직렬화 / 역직렬화

### 직렬화

메모리의 객체(클래스, 인스턴스, 구조체 등)를 저장하거나 전송 가능한 형태(JSON, XML 등)로 변환하는 과정

⇒ 객체는 힙 메모리에 존재하는데 이 메모리 주소나 레이아웃은 그 프로세스가 종료되면 사라짐. 파일에 저장하거나 네트워크로 다른 프로세스에 전달하려면 메모리 구조가 아닌 공통된 형식으로 변환이 필요하기 때문.

* 객체 상태를 저장 가능한 형태로 변환

### 역직렬화

직렬화된 데이터를 다시 프로그램에서 사용할 수 있는 객체로 복원하는 것

* 데이터 형식과 객체 구조가 맞아야 정상적으로 복원 가능

### 정리

직렬화는 메모리에 존재하는 객체나 데이터를 파일에 저장하거나 네트워크로 전송할 수 있는 형태로 변환하는 과정이고, 역직렬화는 그렇게 변환된 데이터를 다시 프로그램에서 사용할 수 있는 객체 형태로 복원하는 과정입니다. 게임에서는 세이브 데이터 저장, 설정 파일, 네트워크 통신 등에 주로 사용됩니다.
