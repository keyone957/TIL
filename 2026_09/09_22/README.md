### 짐벌락 및 해결 방법

#### 짐벌락

오일러 각은 XYZ 세 축을 순서대로 회전시켜 3D 회전을 표현하는 방식입니다.그런데 특정 각도에서 한 축을 회전시키면 다른 두 축의 방향이 겹치는 경우가 생기는데, 이때 겹친 축 중 하나는 회전을 시켜도 나머지 축과 같은 결과를 내어 회전의 자유도 하나를 잃어버립니다.

#### 해결 방법 ⇒ 쿼터니언

쿼터니언은 XYZW 네 개의 값으로 회전을 표현하는데, 오일러 각처럼 세 축을 순서대로 회전시키는 것이 아니라 임의의 하나의 회전축과 그 축을 기준으로 한 회전량을 한 번에 처리합니다.축을 순차적으로 도는 과정 자체가 없기 때문에 축이 겹치는 상황이 발생하지 않아 짐벌락 문제를 해결할 수 있습니다.

### Thread와 Task 차이

#### Thread

OS가 관리하는 저수준 실행 단위. `new Thread()`로 생성하면 OS 레벨의 스레드가 하나 만들어지고 스택 공간 할당과 컨텍스트 스위칭 비용이 크게 듭니다.

* 생성, 종료 비용이 큼
* 스택 메모리를 별도로 가짐
* 실제 실행 흐름 하나를 직접 만듦

#### Task

.NET의 스레드 풀 위에서 동작하는 비동기 작업 단위(비동기 작업을 표현하는 고수준 추상화)입니다.Task를 생성해도 항상 새 스레드가 만들어지는 게 아니라, 스레드 풀에 있는 기존 스레드를 재사용해서 작업을 처리합니다.

* 반드시 새로운 스레드를 만드는 것이 아님
* async / await과 함께 사용하기 편함
* 예외 처리, 결과 반환, 작업 연결이 쉬움
* 짧은 백그라운드 작업이나 비동기 처리에 주로 사용

#### 정리표

|       | Thread                           | Task                         |
| ----- | -------------------------------- | ---------------------------- |
| 관리 주체 | OS 커널                            | .NET 스레드 풀                   |
| 생성 비용 | 큼                                | 작음 ⇒ 풀에서 재사용                 |
| 반환값   | 불가                               | Task<T>로 결과 반환 가능            |
| 예외 처리 | 어려움 (스레드 내부에서 처리)                | try-catch로 async 함수처럼 처리 가능  |
| 용도    | CPU 바운드 작업을 직접 스레드로 오래 점유하고 싶을 때 | I/O 바운드, 짧은 비동기 작업, 병렬 작업 조합 |

### UniTask나 async / await 대신 코루틴을 쓰는 이유??!?

코루틴은 Unity의 프레임 기반 실행 구조와 잘 맞기 때문에 사용합니다. `yield return null`, `WaitForSeconds`, `WaitForFixedUpdate` 등을 이용해서 다음 프레임이나 특정 시간 이후에 작업을 이어가는 로직을 직관적으로 작성할 수 있습니다. 따라서 스킬 연출, 쿨타임, 애니메이션 순차 처리 같은 간단한 게임 로직에서는 코루틴이 편리합니다.반면 반환값이 필요하거나 예외 처리, 병렬 작업 조합이 필요하면 async/await나 UniTask가 더 적합합니다.

### Mono와 IL2CPP 정리

#### Mono, IL2CPP

스크립트를 컴파일하는 방식으로 두 가지 스크립팅 백엔드를 제공합니다.C# 코드를 컴파일하면 먼저 IL로 변환되는데, 이 IL 코드를 실제로 어떻게 실행하느냐가 두 방식의 차이입니다.

#### Mono ⇒ JIT

IL 코드를 런타임에 그때그때 컴파일해서 실행하는 JIT 방식입니다.빌드 속도는 빠르지만 실행 중에 컴파일 과정이 있기 때문에 IL2CPP보다는 성능이 떨어질 수 있습니다.iOS처럼 JIT 자체가 금지된 플랫폼에서는 사용 불가능합니다.

#### IL2CPP ⇒ AOT

실행 전에 IL 코드를 C++로 변환한 뒤 이를 다시 기계어로 미리 컴파일해 두는 AOT 방식입니다.빌드 속도는 오래 걸리지만 런타임에 컴파일 과정이 없기 때문에 실행 성능이 우수합니다.iOS나 WebGL 빌드에서는 필수로 사용됩니다.

#### 왜 성능 차이가 생기는가?

유니티 엔진 자체는 C++로 짜여 있고, 유저가 작성하는 스크립트만 C#입니다. Mono는 이 유저 코드 부분을 런타임에 JIT 컴파일해서 돌리는 반면, IL2CPP는 유저가 작성한 C# 코드까지 전부 C++로 변환해서 미리 네이티브 코드로 컴파일해두기 때문에 실행 시점에 변환 오버헤드가 없어 더 빠르게 동작합니다. 그래서 유니티는 에디터에서 빠른 반복 개발을 위해 Mono를 쓰고, 실제 빌드에서는 IL2CPP를 사용해 생산성과 성능을 둘 다 챙기는 전략을 취합니다.

### Generic Sharing ⇒ IL2CPP AOT 제네릭 문제점 해결 방법?

#### Generic Sharing

IL2CPP가 제네릭 코드를 C++로 변환할 때 코드 크기 폭증을 줄이기 위해 도입한 최적화 기법입니다.제네릭 타입 인자가 참조 타입일 경우 타입마다 별도 코드를 생성하지 않고 하나의 공유된 코드를 재사용하도록 만듭니다.

#### IL2CPP에서 제네릭 문제 상황

제네릭은 타입 안전성과 재사용성을 위한 기능인데, 서로 다른 타입으로 인스턴스화될 때마다 컴파일러가 각 타입 전용 코드를 따로 생성하는 게 일반적인 동작입니다.JIT 방식에서는 그 타입이 런타임에 쓰일 때가 돼서야 코드를 생성하니 문제가 덜하지만, IL2CPP에서는 AOT 방식이라 빌드 시점에 나올 수 있는 모든 타입 조합의 코드를 미리 다 생성해둬야 합니다. 이것 때문에 AOT의 코드 사이즈와 빌드 시간이 늘어납니다.

#### 해결 방안 ⇒ Generic Sharing 사용

타입 인자의 종류에 따라 다르게 처리합니다.

* **참조 타입** ⇒ 내부적으로 객체에 대한 참조를 다루기 때문에 여러 타입이 동일한 형태의 구현을 공유하기 쉬움
* **값 타입** ⇒ 타입마다 크기, 메모리 배치, 연산 방식 등이 달라질 수 있기 때문에 참조 타입보다 코드를 공유하기 어려움

따라서 값 타입 제네릭은 경우에 따라 타입별로 별도의 코드가 생성될 수 있고, 많은 값 타입과 제네릭 조합을 사용하면 IL2CPP 빌드 시간과 코드 크기가 증가할 수 있습니다. 어쩔 수 없이 값 타입 제네릭은 타입별로 코드가 생성됩니다.
