#### 스택 할당이 힙 할당보다 일반적으로 빠른 이유는 무엇인가요?

스택 할당이 힙 할당보다 일반적으로 빠른 이유는 스택이 LIFO 구조로 관리되기 때문에 메모리 할당 시 Stack Pointer를 이동하고, 해제 시 이전 위치로 복원하는 정도로 처리할 수 있기 때문입니다.반면 힙은 요청한 크기에 맞는 빈 메모리 공간을 찾아야 하고, 블록 분할이나 병합, 메타데이터 관리 등의 추가 작업이 필요합니다. 또한 스택은 메모리가 연속적으로 사용되는 경우가 많아 캐시 지역성 측면에서도 유리합니다.

### 컨텍스트 스위칭? | 컨텍스트 스위칭의 오버헤드

### 컨텍스트 스위칭

현재 실행 중인 프로세스 OR 스레드의 컨텍스트를 저장하고 다음에 실행할 프로세스의 컨텍스트를 복원하는 과정

예시)

프로세스 A

↓

A의 실행 상태 (Context) 저장

↓

프로세스 B

↓

B의 실행 상태(Context) 복원

### 컨텍스트 스위칭의 오버헤드

문맥 교환이 많으면 현재 프로세스나 스레드의 레지스터 상태를 저장하고 다음 작업의 상태를 복원하는 오버헤드가 반복적으로 발생하기 때문에 성능이 저하될 수 있습니다.또한 실행 대상이 바뀌면서 CPU Cache와 TLB의 지역성이 깨져 Cache Miss나 TLB Miss가 증가할 수 있습니다. 따라서 CPU가 실제 프로그램 로직을 실행하는 시간보다 상태 전환에 사용하는 시간이 많아지면 전체 처리량이 감소하게 됩니다.

### 시스템 콜?? system call

### 정의

사용자 모드에서 실행되고 있는 프로그램이 커널 모드의 기능을 사용하고 싶을 때 OS 커널에게 요청을 보내는 인터페이스

### 필요 이유

일반 프로그램은 사용자모드에서 실행이 되는데 이 모드에서 하드웨어에 직접 접근하거나 다른 프로세스의 메모리를 건드릴 수 없음

반면 파일을 읽거나 메모리를 새로 할당 받거나 화면에 출력하는 것 같은 작업은 실제로 하드웨어나 커널 내부 자원을 다뤄야 함. 이 권한은 커널 모드에서만 가능하므로 사용자 프로그램은 직접 할 수 없고 커널에게 대신 해달라고 요청해야함. 이때 사용하는 것이 시스템 콜

### 동작 과정

1. 사용자 프로그램이 시스템 콜 실행 (예: `read()`, `write()`, `fork()`)
2. CPU가 **트랩(trap)** 명령어를 실행하며 사용자 모드 → 커널 모드로 전환
3. 커널이 요청된 작업(파일 읽기, 메모리 할당 등)을 대신 수행
4. 작업 완료 후 결과를 반환하며 다시 커널 모드 → 사용자 모드로 복귀
5. 프로그램은 원래 실행 흐름을 이어감

### 비용

⇒ 시스템 콜은 일반 함수 호출보다 비용이 크다

유저 모드 → 커널 모드 전환

CPU 상태 일부 저장

커널 코드 실행

결과 반환

커널 모드 → 유저 모드 전환

이런 과정때문에 너무 잦은 시스템 콜은 성능 저하로 이어질 수 있음

### 게임 개발

* 파일 IO(에셋 로딩, 세이브 파일 읽기 쓰기)는 결국 내부적으로 시스템 콜을 호출함 ⇒ 매 프레임 파일을 열고 닫는 대신 필요한 시점에 미리 로드 + 메모리에 캐싱해두는 방식 사용
* 소켓 통신도 시스템 콜 기반이라 패킷을 하나씩 보내는 대신 여러 데이터를 모아 배치로 전송하는게 성능에 유리
* 유니티의 Debug.Log 도 내부적으로 시스템 콜을 유발할 수 있어서 매 프레임 대량으로 호출하면 성능 저하의 원인이 됨

### 정리

시스템 콜은 사용자 프로그램이 운영체제 커널의 기능을 사용하기 위해 요청하는 인터페이스입니다.사용자 프로그램은 유저 모드에서 실행되기 때문에 파일 IO, 프로세스 생성, 메모리 관리 같은 커널 기능에 직접 접근할 수 없습니다. 따라서 시스템 콜을 통해 커널 모드로 전환하여 운영체제가 해당 작업을 수행하고 결과를 받은 뒤 다시 유저모드로 돌아옵니다.이 과정에서 모드 전환과 상태 저장 등의 오버헤드가 발생하기 때문에 일반 함수 호출보다 비용이 큽니다.

### 스레드마다 별도의 스택이 필요한 이유?

각 스레드는 서로 독립적인 실행 흐름을 가지기 때문에 함수 호출 정보와 지역 변수도 각각 따로 관리해야함.

스택에는 대표적으로 아래 값들을 저장해 놓고 있음

* 함수의 지역변수
* 매개변수
* 함수 반환주소
* 호출된 함수의 스택 프레임

예를 들어 두 스레드가 동시에 같은 함수를 실행한다고 하자.
    void Test()
    {
        int value = 10;
    }

스레드 a와 스레드 b가 동시에 test함수를 실행하면 각자 자신의 value를 가지고 있어야함

근데 만일 스택을 하나만 공유한다면?

각 스레드의 독립적으로 가져야할 값이 공유가 되어지역 변수, 반환주소, 함수 호출순서 꼬임, 실행흐름이 손상될 수 있음

### 정리

스레드마다 별도의 스택이 필요한 이유는 각 스레드가 독립적인 실행 흐름을 가지기 때문입니다.스택에는 함수 호출 정보, 지역 변수, 매개변수, 반환 주소 등이 저장되는데, 여러 스레드가 하나의 스택을 공유하면 서로의 함수 호출과 지역 변수가 충돌할 수 있습니다.따라서 같은 프로세스의 스레드들은 Heap과 Code 영역은 공유하지만, Stack과 Register, Program Counter 같은 실행 상태는 각자 독립적으로 가지고 있습니다.

### 클라이언트와 서버의 역할

클라이언트 : 사용자의 입력을 받아 서버에 요청하고 결과를 화면에 표현하는 역할

서버 : 요청을 처리하고 게임의 중요한 상태와 규칙을 관리하는 역할

### 유저 영역 VS 커널 영역 ⇒ 나눈 이유?

### 유저 영역

일반 애플리케이션이 실행되는 영역으로, 하드웨어와 시스템 자원에 직접 접근할 수 없는 제한된 공간입니다.

### 커널 영역

운영체제의 핵심이 실행되는 영역으로, 메모리·프로세스·하드웨어를 직접 제어할 수 있는 공간입니다.

### 커널, 유저 영역을 나눈 이유?

1. 시스템 안정성 보호
   * 사용자가 작성한 프로그램은 버그가 있을 수 있음. 만약 이런 프로그램이 하드웨어나 커널 메모리에 직접 접근할 수 있다면 이런 잘못된 명령 하나로 시스템이 전체 다운되거나 다른 프로세스의 메모리를 망가뜨릴 수 있음.
2. 보안
   * 사용자 프로그램이 커널이나 다른 프로세스에 마음대로 접근하지 못하도록 제한
3. 자원의 중앙 관리, 자원 보호
   * CPU, 메모리, 디스크 장치 등의 중요한 자원을 운영체제가 통제

일반 프로그램을 사용자 모드에서 제한된 권한으로 실행시켜 커널 메모리나 하드웨어에 직접 접근하지 못하게 하고, 필요한 기능은 시스템 콜을 통해 커널에 요청하도록 합니다.이를 통해 하나의 프로그램에서 버그나 악의적인 동작이 발생하더라도 운영체제 전체나 다른 프로세스에 영향을 주는 것을 방지할 수 있습니다.
