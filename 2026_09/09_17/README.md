### Update문

### FixedUpdate

> 고정된 시간 간격으로 호출. 프레임 레이트와 무관하게 항상 일정한 간격으로 실행됨 ⇒ 기본 0.02초 50Hz

* Time.fixedDeltaTime 기반

### FixedUpdate에서 물리 처리 하는 이유

> 일정 시간 간격으로 호출 되기 때문에 프레임 변화에 영향을 덜 받고 물리 계산을 안정적으로 처리할 수 있어서

### Update

> 매 프레임마다 한 번 호출되는 함수.
> 호출 주기가 프레임레이트에 따라 가변적이라 하드웨어 성능에 따라 호출횟수가 달라짐

### LateUpdate

> 모든 Update 이후에 호출되는 함수로 한 프레임에서 모든 오브젝트의 Update가 끝난 뒤 실행이 됨.

#### 사용처

→ LateUpdate는 렌더링이 수행되기 직전에 실행되기 때문에 다른 오브젝트의 최종상태를 기준으로 처리해야하는 로직 , 특히 카메라 추적과 같은 경우에 적합함.
→ 렌더링이 수행되기 직전에 보정하는 요도로도 적합함 즉 카메라와 같이 최종 시점에 영향을 주는 요소는 LateUpdate에서 처리하는 것이 자연스러움

### LateUpdate에서 카메라 후처리 하는 이유

> 모든 update이후 호출 되기 때문에 플레이어의 이동이 완료된 최종 위치를 기준으로 카메라를 따라가게 할 수 있어서 카메라 추적이나 후처리에 적합함
> 카메라가 캐릭터를 따라가려면, **캐릭터의 위치가 이미 이번 프레임에 확정된 뒤에** 카메라가 그 위치를 보고 움직여야 함.

문제는 `Update()` 끼리는 **실행 순서가 보장되지 않음** — 캐릭터 이동 스크립트의 `Update()`와 카메라 스크립트의 `Update()` 중 뭐가 먼저 실행될지 알 수 없음. 만약 카메라가 캐릭터보다 먼저 실행되면, 카메라는 **한 프레임 전(갱신 안 된) 위치**를 기준으로 움직이게 되어 미세하게 밀리는 떨림(jitter) 현상이 생김.
`LateUpdate()`는 **모든 오브젝트의 Update()가 다 끝난 뒤**에 호출되는 게 보장되므로, 이 시점엔 캐릭터 위치가 확실히 최신 상태임 → 카메라가 그 확정된 위치를 안전하게 참조 가능.

### 꼬리 질문

* FPS가 낮아서 한 프레임을 렌더링하는데 0.1초가 걸렸다고 가정해보자 이때 FixedUpdate는 어떻게 되는가?
  * 다음 프레임에서 기본 값(Time.fixedDeltaTime = 0.02) 기준 5회 호출됨
* 그랬을 때 발생하는 문제점은 무엇인가
  * FixedUpdate 누적 호출로 인한 CPU 과부하로 프레임이 더 지연됨
    * 더 지연되면서 다음 프레임 FixedUpdate 호출 횟수 더 증가(악순환)
  * 순간적으로 많은 물리연산으로 인한 물리 시뮬레이션 오류
    * 한 프레임에 물체가 너무 멀리 이동하여 충돌 감지 못하고 통과할 수도 있음
* 해결 방법은?
  * Maximum Allowed Timestep을 조절하여 일정 부분만 누적 처리하고 나머지는 버림
    * 한 프레임이 1초 걸려도 0.33초(기본 값)까지만 FixedUpdate로 처리하고 나머지 0.67초는 버림
    * 물리 시뮬레이션이 느려지는 것처럼 보임
    * 완전히 멈추는 것보다는 느려지는 게 낫다고 판단
* 왜 3가지로 나누는가?
  * 물리 안정성, 렌더링 일관성, 입력 및 게임 로직의 정확성을 확보하기 위해
  * FixedUpdate는 물리 로직을 위해 존재
    * 물리엔진은 일정한 시간 간격에서의 상태 변화를 가정해 계산함
    * Update에 섞어 버리면 하드웨어에 따라 결과가 달라지고, 충돌 누락, 떨림, 관성 오차 등이 생김
  * LateUpdate는 후처리를 위해 존재
    * 스크립트 실행 순서와 관계없이 모든 Update가 끝나고 실행되기 때문에 항상 최종 상태를 보장함

### ref out in

> 매개변수를 참조로 전달하는 세가지 키워드.
> 
> c#은 값타입을 값복사로 넘기는데 이 키워드를 사용하면 변수의 메모리 주소를 전달해서 함수 내부에서 원본을 직접 다룰 수 있음

### ref ⇒ 읽기 O / 수정 O

> 원본 변수를 직접 읽고 수정할 때 사용

* 호출 전에 반드시 초기화되어 있어야함.

* 함수 안에서 **초기화 여부와 상관없이** 자유롭게 읽고 쓸 수 있음

* `코드`
  
      void AddOne(ref int x)
      {
          x = x + 1;
      }
      
      int a = 10;
      AddOne(ref a);
      // a = 11
  
  

### out ⇒ 초기값 읽기 X / 수정 O

* 초기화 하지 않아도 넘길 수 있음

* 반드시 메서드 내에서 할당 해줘야함
  
  * 함수 종료 전까지 모든 코드 경로에서 값을 할당하지 않으면 컴파일 에러
  
  * * *

* `코드`
  
      bool TryParse(string s, out int result)
      {
          if (int.TryParse(s, out result)) return true;
          result = 0;
          return false;
      }
      
      int value;
      TryParse("123", out value);
      // value = 123
  
  

### in ⇒ 읽기 O / 수정 X

* 반드시 초기화해서 넘겨야함

* 큰 구조체를 함수에 넘길 때 값 복사 비용을 없애면서도 원본 훼손을 막고 싶을 때 사용

* `코드`
  
      struct BigStruct { public int A, B, C, D; /* ... */ }
      
      void PrintData(in BigStruct data)
      {
          // data.A = 5; // 컴파일 에러! 수정 불가
          Console.WriteLine(data.A);
      }
  
  

### 꼬리 질문

**Q. ref와 out의 내부 구현 차이는?**

IL 수준에서 둘 다 포인터(주소)를 넘기는 건 동일함.

차이는 **컴파일러의 정적 검사** 수준에 있음 —

`out`은 "함수 종료 시점에 반드시 값이 채워져 있어야 함"을 컴파일러가 강제하고,

`ref`는 "호출 전 이미 값이 있어야 함"을 강제하는 차이.

**Q. in을 쓰면 항상 성능이 좋아지나?**

아니다. `in`은 참조로 넘기므로 포인터 역참조(dereference) 비용이 생김. 구조체 크기가 포인터(8바이트)보다 작으면 오히려 값 복사가 더 빠를 수 있음. 큰 구조체일 때만 이득.
