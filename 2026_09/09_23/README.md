### 포워드 렌더링, 디퍼드 렌더링

#### 포워드 렌더링

오브젝트를 그릴 때 해당 오브젝트에 영향을 주는 조명을 바로 계산하는 방식입니다.

* **동작원리**
  → 하나의 오브젝트를 그릴 때마다 해당 오브젝트에 영향을 주는 모든 빛 연산을 셰이더에서 즉시 처리함. 오브젝트 개수 x 빛의 개수만큼 연산이 발생함

* **장점**
  
  * 투명도 처리가 자연스러움
  * 연산 구조가 단순하여 사양이 낮은 모바일 기기에 적합
  * 메모리 사용량이 적음
  * MSAA 사용에 유리

* **단점**
  
  * 조명이 많아질수록 계산량이 폭증함
  * 모든 조명을 한 번에 계산하므로 비효율적
  * 라이트별로 드로우콜 증가

#### 디퍼드 렌더링

먼저 오브젝트의 색상, Normal, Depth, Material 정보 등을 G-Buffer에 저장하고 이후 조명을 한꺼번에 계산하는 방식입니다.물체의 정보를 먼저 G-버퍼에 저장한 후 나중에 한 번에 라이팅을 계산합니다.

→ 카메라가 보는 화면 기준으로 각 픽셀의 기하 정보를 먼저 저장한 뒤 화면 공간에서 조명을 계산하는 방식

→ 오브젝트 단위가 아니라 현재 화면에 보이는 픽셀 단위로 빛을 처리함

* **장점**
  
  * 조명이 많아도 조명 수에 비례하지 않으므로 효율적
    * 포워드 계산량 : 오브젝트 수 x 라이트
    * 디퍼드 계산량 : 픽셀 x 라이트
  * 라이트를 추가하는 비용이 적음
    * 포워드 : 모든 오브젝트를 다시 계산
    * 디퍼드 : 화면 픽셀만 한 번 더 계산

* **단점**
  
  * 메모리 사용량이 많음
  
  * 투명도 처리가 어려움
    → 디퍼드 렌더링은 G-buffer에 각 픽셀의 기하 정보를 하나만 저장하는 구조이기 때문에 여러 개의 투명 객체가 겹칠 경우 모든 정보를 동시에 표현할 수 없습니다.
    → 투명 객체는 뒤에 있는 색과의 블렌딩 순서가 중요한데, 디퍼드 렌더링은 화면 단위로 조명을 한 번에 계산하는 방식이라 이러한 순서 기반 처리가 어렵습니다.
    ⇒ 따라서 투명도 처리를 할 객체는 포워드 렌더링으로 섞어서 처리합니다.

### 왜 URP → 포워드 / HDRP → 디퍼드 렌더링을 사용함??

#### URP → 포워드 렌더링

URP는 모바일을 포함한 다양한 저사양 플랫폼까지 폭넓게 지원하는 것을 목표로 합니다. 디퍼드는 G-Buffer 때문에 메모리 대역폭 사용량이 큰데, 모바일 GPU는 대역폭이 병목이 되기 쉬워 불리합니다.반면 포워드는 구조가 단순하고 메모리 사용량이 적으며, 라이트 수가 상대적으로 적은 모바일·저사양 환경에 적합합니다.

#### HDRP → 디퍼드 렌더링

HDRP는 고사양 PC, 콘솔을 타겟으로 하고 다이내믹 라이트를 많이 쓰는 고품질 그래픽을 지향합니다.라이트 수가 많아질수록 포워드는 오브젝트 수 x 라이트 수로 연산이 폭증하지만, 디퍼드는 픽셀 수 x 라이트 수로 라이트 증가에 훨씬 덜 민감합니다.따라서 다수의 광원을 다뤄야 하는 HDRP는 디퍼드를 기본으로 채택하고, 투명 객체처럼 디퍼드가 취약한 부분만 포워드로 섞어서 보완합니다.

### Allocation / GC.Alloc / GC.Collect

#### Allocation

프로그램이 실행 중에 새로운 메모리 공간을 확보하는 것입니다.

ex)
    var list = new List<int>();

⇒ 새로운 객체를 위한 메모리 할당 발생.

#### GC.Alloc

유니티 프로파일러에서 힙에 새롭게 할당된 메모리 양을 나타내는 항목입니다.

Allocation 발생 ⇒ 프로파일러에서 GC.Alloc으로 표시

#### GC.Collect

더 이상 사용하지 않는 힙의 객체를 찾아 메모리를 회수하는 과정입니다.

**과정**

1. Allocation 발생
2. GC.Alloc 증가
3. 사용하지 않는 객체 누적
4. GC 실행
5. 가비지 메모리 회수

⇒ GC가 실행되는 순간 처리 비용이 발생
